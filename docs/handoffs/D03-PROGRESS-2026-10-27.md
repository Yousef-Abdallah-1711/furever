## F. Database and access-control implementation

The breed catalog seeds 44 stable English/Arabic cat and dog breeds and uses the existing audited administrative write pattern. Pet ownership is tied to the authenticated profile, and the foreign key prevents selecting a breed from another species. Pet RLS and Storage authorization require an active owner account, completed profile, populated city, configured bilingual legal documents, and matching current Terms/Privacy consent versions. This preserves the D02 fail-closed onboarding gate.

The client cannot set `owner_id`, `deleted_at`, or system timestamps directly and cannot hard-delete pets. The `delete_pet` RPC is the soft-delete boundary. Storage is private and authorized by both owner folder and actual active pet row; path strings alone do not establish access. Clinics receive no access in D03.

## G. Attachment implementation

The uploader uses Expo SDK 57 compatible image picker, image manipulator, and document picker packages. Images are resized before upload; MIME and 10 MiB limits are checked; upload paths use owner/pet/random filename segments; overwrite/upsert is disabled. Failed operations can be retried. Native upload progress uses the upload task; web progress is staged only.

The viewer creates a short-lived signed URL and supports native image pinch. The current PDF action opens the signed URL in the system browser. The task asks for an in-app PDF preview, so T225 and T235 remain partial.

## H. Local Storage integration

`backend/supabase/scripts/verify-pet-storage-local.mjs` passed **20/20** local checks using disposable owners, pets and files. It covered allowed upload/download, anonymous and cross-owner denial, mismatched pet IDs, overwrite denial, MIME/size rejection, cross-owner deletion denial, and access denial for suspended/deleted owners or soft-deleted pets. Fixtures and files were removed and the previous legal-config value restored. No database reset or hosted project access occurred.
